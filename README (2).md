# Inventory Tracker (CS 360)

Inventory Tracker is an Android app I built in Java with a SQLite database. You log in, keep a list of items and how many of each you have, and the app texts you when something is running low. The full Android Studio project is in `InventoryTracker.zip`, and my launch plan is included as a Word document.

## Reflection

I made this app for people who keep a small stock of things, like a small business owner or a family that buys supplies in bulk, and who don't want to find out something ran out only after it already did. The app had to let someone log in, or create an account if they'd never used it, and save their items in a database that is still there after the app closes. It also had to show those items in a grid and let the user add, change, and delete them. The part that tied it together for me was the alert. If an item gets low, the app should tell you so you don't have to keep checking. Not everyone wants an app sending texts, so I also needed the app to work normally if someone says no to that permission.

To support that, I kept the screens simple. The login screen has a username, a password with a "show password" box, and an optional phone number for alerts, so a new person can sign up on the same screen without any extra steps. The main screen shows a quick summary at the top, a search box, and the grid of items. Each item has its own card with + and - buttons, because changing a quantity is what people will do most, so I wanted it to take one tap. Edit and Delete are there for everything else. Low items turn red and say "LOW," and I added a confirmation before deleting so nobody loses an item by accident. I think the design works because there is hardly anything to learn. You can open it and know what to do.

When I started coding, I built the app one layer at a time so I always had something working to test. The database came first, then the login, then the grid, and the text alerts last. I put all the SQL in one `DatabaseHelper` class so the screens never deal with raw queries, and I moved the text message code into its own small `SmsHelper` class to keep the main screen's code from getting crowded. I tried to use names that make sense to someone reading it for the first time and to write comments that explain why I did something, not just what the line does. I also stored passwords as salted hashes instead of plain text. I plan to use the same habits on future projects, because splitting the data, screen, and feature code apart makes bugs much easier to find.

I tested by running the app in the Android Studio emulator and going through every feature by hand. I created an account, logged in with the right and wrong password, added, edited, and deleted items, used the + and - buttons, searched, and closed and reopened the app to make sure the data was still there. I tested the text alerts twice, once allowing the permission and once denying it, to confirm the rest of the app kept working when alerts were off. Testing matters because an app isn't finished until it works for a real person, including when they enter the wrong thing or say no to a permission. It also caught things I would not have noticed from the code alone, like screens that were hard to read until I set the colors myself, and the add dialog closing on me when I typed something wrong.

The hardest part wasn't any single feature, it was getting the project to build and run on my own computer. I hit one problem after another: the Gradle version didn't match the Java version on my machine, the Android SDK version the project wanted wasn't installed, and the emulator showed only a black screen. Each time I had to slow down, actually read what the error was saying, and figure out the cause instead of changing things at random. I matched the Gradle and plugin versions, switched the project to an SDK I already had, and tried a different emulator setup until the app finally ran. It was frustrating, but it taught me how to troubleshoot step by step, which I know I'll need on the job.

The part I'm most proud of is how the text message permission is handled. The app asks at a reasonable time and remembers the answer. If permission is granted, it sends the text alert. If it's denied, the user still gets a warning on screen and can tap the status line later to turn alerts on. I wanted the "no" answer to feel like a normal choice and not a broken app, and I think that shows I thought about how real users behave. The database work comes in a close second, with create, read, update, and delete all working and a migration that keeps old data when I changed the table.
